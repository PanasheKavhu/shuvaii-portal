## Go-live checklist

What must be true before the first real school uses the portal. Each item says who does it and where; the how is in `docs/DEPLOY.md` (hosting), `docs/BACKUPS.md` and `docs/RETENTION.md`. "Panashe" means whoever operates the platform (Panashe or Shuvai).

**Legal (blocker, Q20)**

- [ ] **Lawyer, arranged by Panashe; repository:** review `/privacy` and `/terms` (wording in `src/lib/privacy/notice.ts`); then remove the "Draft" banner (`LEGAL_REVIEW_NOTE`), set a new `PRIVACY_NOTICE_VERSION`, and record the review in `docs/DECISIONS.md` and `OPEN_QUESTIONS.md` Q20 (D57). Both pages are marked "to be reviewed by a lawyer before go-live" until then.
- [ ] **Pilot school's head, with Panashe; in person:** confirm the school accepts data stored in the chosen Supabase region and names its data protection contact (Q20).

**Supabase dashboard (production project; staging first): Panashe**

- [ ] **Project creation:** region closest to Zimbabwe that Supabase offers, Pro plan (daily backups, no pausing); the same region for staging (DEPLOY section 1).
- [ ] **Authentication, Sign In / Providers:** "Allow new users to sign up" off, email sign in on: every account is made by the server (D27).
- [ ] **Authentication, URL Configuration:** Site URL = `SITE_URL`, Redirect URLs `SITE_URL/**` (D14, D19).
- [ ] **Authentication, Emails, SMTP Settings:** a real sender; the built-in one cannot deliver school invites and resets.
- [ ] **Authentication, Emails, Templates:** invite from `supabase/templates/invite.html` (subject and the `/auth/confirm?token_hash=...&type=invite` link, D14); reset password from `supabase/templates/recovery.html` (D19).
- [ ] **Authentication, Multi-Factor:** keep "Authenticator app (TOTP)" enabled (D54).
- [ ] **Authentication, Rate Limits:** raise `sign_in_sign_ups`: a class of learners signs in from one school address (D26).
- [ ] **Project Settings, Data API:** exposed schemas `public` only (D2). **Database, Settings:** enforce SSL.
- [ ] **Terminal (Supabase CLI):** `supabase db push` to staging, check, then production (DEPLOY section 5).

**Vercel dashboard: Panashe**

- [ ] **Settings, Environment Variables (Production and Preview separately):** `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `SITE_URL` (QR codes and share links; production refuses PDFs without it, D45, D47, D48), `LEARNER_PIN_SECRET` (32+ random characters, never changed: changing it stops every learner PIN, D26), `DATA_REGION` (printed on the privacy notice, D57), `CRON_SECRET` (D58), `SENTRY_DSN`, `NEXT_PUBLIC_SENTRY_DSN`, `NEXT_PUBLIC_SENTRY_ENVIRONMENT` (D59). Secrets also go in the password manager.
- [ ] **Settings, Functions:** function region next to the Supabase region.
- [ ] **Settings, Domains:** the one portal domain (DEPLOY section 6).
- [ ] **Settings, Cron Jobs:** after the first production deploy, `/api/cron/retention` is listed daily at 01:00 UTC; the next day its log shows counts, not 401 (D58).
- [ ] **Settings, Logs / Log Drains:** no drain that keeps request URLs for long; the audit and People search boxes carry learner names in `?q=` (D37; the overview's search posts instead, D51).
- [ ] **Browser, after the first deploy:** check that a forged `x-real-ip` / `x-forwarded-for` header does not change the address the app counts tries by (verification page, share links, learner sign in, D48).
- [ ] **Plan:** Pro (Hobby is non-commercial).

**GitHub repository settings: Panashe (repository owner)**

- [ ] **Settings, Branches, `main`:** require pull requests and the status checks `check`, `db` and `e2e` before merging (D61).
- [ ] **Settings, Secrets and variables, Actions:** `BACKUP_DB_URL`, `BACKUP_SUPABASE_URL`, `BACKUP_SERVICE_ROLE_KEY`, `BACKUP_PASSPHRASE` for the weekly backup; then run "Weekly backup" once by hand and check it uploads an artifact (D60).

**Monitoring: Panashe**

- [ ] **Sentry:** create the organisation (EU data region if offered) and a Next.js project; copy the DSN to Vercel; in the project's Security and Privacy settings keep the data scrubber on and turn on "Prevent storing of IP addresses"; trigger one test error on staging and check it arrives without names, marks or tokens (D59).
- [ ] **Uptime monitor (UptimeRobot, Better Stack or similar):** check `https://<portal>/healthz` every 5 minutes and alert Panashe and Shuvai (D59).

**Backups: Panashe**

- [ ] **Hosted scratch project:** run the restore test from the first production backup into a new scratch Supabase project, run `supabase test db --db-url` against it, and record the result here (`docs/BACKUPS.md`). The local run passed on 2026-10-13.
- [ ] **Monthly:** download the newest backup artifact and keep a copy outside GitHub.

**Platform and the pilot school**

- [ ] **Console, Panashe:** each super admin sets up two-factor at their first sign in and saves the recovery codes somewhere safe (D54).
- [ ] **Console, then `/admin/setup/privacy`, pilot school admin:** the privacy contact filled in; `/privacy?school=<slug>` shows it (D57).
- [ ] **`/admin/setup`, pilot school admin with Panashe:** the school's own bands entered and checked against a past report: each grade level's scale matches the school's key at every boundary (for example 70, 60, 50, 45, 40 on the O-level sample), and a past report's marks give the grades printed on it (Q1, D38). The seed school still uses the O-level sample key, under which a 70 is an A.
- [ ] **On paper, pilot school's head:** print one published report in black and white and check it by eye (D45).
